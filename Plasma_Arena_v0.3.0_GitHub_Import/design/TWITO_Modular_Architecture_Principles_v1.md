# עקרונות ארכיטקטורה ופיתוח מודולרי
## מסמך יסוד רוחבי לפרויקטים — TWITO / STAN FAN / Rafael Brothers

**גרסה:** 1.0  |  **תאריך:** 27.10.2026  |  **מעמד:** הנחיות תכנון מומלצות, לא אישור לכך שהיכולות כבר הוטמעו

> **כלל היסוד:** קודם מייצבים את הליבה, מפרידים נתונים מהתנהגות ומגדירים מקור אמת ואחריות; רק אז מרחיבים את התוכן, הכלים והאוטומציה.

## א. למה המסמך נועד?

לייצר שיטת פיתוח עקבית שאפשר להתאים למשחקים, כלי הפקה יצירתיים, פלאגינים ומערכות ניהול. היעד אינו לאחד את הפרויקטים למערכת אחת, אלא לשתף עקרונות שמפחיתים כפילויות, סיכוני רגרסיה ותלות בין רכיבים. **המסמך אינו מחליף Architecture Audit ייעודי לכל פרויקט.**

## ב. עשרת העקרונות

### 1. מתחילים מנקודת מוצא מאומתת

לפני שינוי, מזהים את **הגרסה המותקנת**, **קוד המקור**, **גרסת המידע** ו**הבדיקות שעברו בפועל**. גרסת פלאגין, גרסת סקיל, ענף GitHub וטיוטת PR אינם בהכרח אותו דבר. שומרים Baseline, Release Manifest ונתיב חזרה לאחור. אין לקדם תכנון או דיווח היסטורי לסטטוס של יכולת שכבר פועלת.

### 2. מפרידים ליבת התנהגות מנתוני תוכן

**Core:** מנגנונים וכללי פעולה שנשארים יציבים בין שלבים, הפקות או פרויקטים.

**Data / Configuration:** מה קיים, היכן, לאיזו גרסה הוא שייך ומהם פרמטרי הפעולה שלו.

**Reusable Components:** מימושים חוזרים שניתנים להפעלה באמצעות הגדרות, לא באמצעות שכפול קוד.

**Views / Exports:** תצוגות ומסמכים הנגזרים מהמידע — אינם מקור אמת נוסף.

השאיפה: הוספת שלב או סצנה ושינוי מיקום, תפקיד או נכס צריכים לדרוש בעיקר שינוי נתונים, לא שינוי ליבת המערכת.

### 3. מודולריות לפי אחריות, לא לפי מספר קבצים

לכל מודול חוזה כניסה/יציאה, אחריות מוגדרת, תלויות מצומצמות ומחזור חיים ברור. רכיבים מתוכננים לשימוש חוזר, אך אין להפוך כל קובץ, תפקיד או פונקציה לפלאגין נפרד. הימנעו ממסדי נתונים חדשים, microservices או מערכות אירועים מורכבות ללא צורך מדיד.

### 4. מקור אמת יחיד ובעל אחריות אחד לכל סוג מידע

לכל ישות קובעים **Owner**, מקור מוסמך, מזהה וקשר לרשומות אחרות. שכפולים מוחלפים בקישורים, מזהים והפניות מוצמדות לגרסה. למשל, עדכון מיקום עץ צריך להזיז יחד גרפיקה, התנגשות וטריגרים; שינוי נכס בבייבל צריך להשפיע רק על השוטים המתייחסים אליו — בלי לדרוס גרסאות היסטוריות.

### 5. נתונים בעלי סכמה, מזהים וגרסאות

רשומות משתמשות במזהים יציבים (`record_id`), `schema_version`, `version` או `revision`, שיוך לפרויקט, מקור נתונים וקשרים. שינוי סכמה מחייב Validation, בדיקת תאימות לאחור ומסלול Migration; שוט או תוצר שכבר נוצר מוצמד לגרסת הנכס המקורית, לא אוטומטית ל־`latest`.

### 6. מפרידים מידע גולמי, נכסים ותצוגות

קוד, JSON/Markdown, תמונות/וידאו, תבניות ותוצרי HTML נשמרים בהתאם לתפקידם. קובץ מקור מדיה נשמר במקום מוסמך, previews קלים נגזרים ממנו, ו־HTML/דוחות נוצרים מהנתונים במקום להתעדכן בנפרד. חבילות ZIP משמשות checkpoints או העברה, עם Manifest ו־hash, ולא הופכות לאוסף בלתי מבוקר של עותקים.

### 7. ממשקים חיצוניים הם שכבה עצמאית ומדורגת

מחברים GitHub, Drive, Higgsfield או פלאגינים אחרים דרך **Adapters** וחוזי מידע ברורים. מתחילים בקריאה מאומתת ובבדיקת זהות החשבון, המשאב והגרסה; רק אחר כך שוקלים כתיבה עם Diff, אישור, בדיקת קונפליקט ו־Readback. אין לפרש קיומה של טיוטת אינטגרציה כהוכחת חיבור חי.

### 8. הרשאות ואישורים הם חלק מהארכיטקטורה

יש להפריד בין **Completed תפעולי**, **QA Passed**, ו־**Approved יצירתי או עסקי**. סוכן או כלי אינם מאשרים שינוי קאנון, הוצאה כספית, מחיקה, פרסום או מתן הרשאה במקום הבעלים המוסמך. כל אישור מהותי זקוק לראיה ומסגרת תחולה, לא רק לערך `approved: true` במסמך.

### 9. פיתוח הדרגתי עם בדיקות והוכחת שימור יכולות

מחזור עבודה מחייב: **AUDIT → BASELINE → DESIGN → SMALL CHANGE → QA → FIX → RETEST → CHECKPOINT**. יש לבצע קודם Proof of Concept מצומצם, ואז להעביר בהדרגה רכיבים קיימים. מבחינים בין קריאת קוד לבין הרצה מוצלחת, בין סימולציה לבין בדיקת דפדפן, ובין QA מבני לבין אישור אמנותי. בדוח מופיעים גם תחומים שלא נבדקו.

### 10. תיאום בין פרויקטים ללא אובדן עצמאות

כל פרויקט נשאר אחראי לקוד, לנכסים, לתהליכים ולמקורות המידע הפנימיים שלו. כלי תיאום רוחבי מקבל רק **מזהה, מיילסטון, סטטוס, חסם וקישור מאושר** — לא משכפל Production Bible, לא הופך למנהל שוטים ולא מחליף את מנהל המשימות הפנימי. גבולות חשבונות והרשאות נשמרים במפורש.

## ג. איך העקרונות מיושמים בפרויקטים שלנו?

### Rafael Brothers — האחים רפאל

- **ליבה:** פיזיקת סרט המדידה, תנועת דמויות, התנגשות ומצלמה.
- **נתוני שלב:** מיקום עצים, תהומות, אויבים, נקודות עגינה, רקעים וטריגרים באמצעות Stage JSON בעל סכמה.
- **ספריית רכיבים:** עץ מתפורר, גשר, רשת דביקה, אויב ונקודת עגינה — מימוש אחד, מופעים רבים.
- **תוצר נגזר:** Build של HTML עצמאי מתוך מקור מודולרי.
- **כלי חיצוני:** Platformer Challenge Forge מתכנן ובודק אתגרים; הוא אינו מחליף את פיזיקת המשחק או את בדיקת העבירות בדפדפן.

### STAN FAN Studio HQ — הפקות ובייבל חי

- **ליבה:** ארבעת תפקידי העבודה הקיימים, Work Orders, Hand-offs, גרסאות ומנגנון אישורים.
- **נתוני הפקה:** Production → Scene → Shot → Element / Asset Revision → Decision / Approval, עם מזהים והפניות מדויקות.
- **מקורות אמת:** משימות תפעוליות ב־GitHub כאשר המיפוי מאומת; קאנון ומדיה במקור הפקה מוסמך; HTML כתצוגה בלבד.
- **מבחן הצלחה:** שינוי גרסת עיצוב דמות מזהה את השוטים המושפעים בלי לדרוס את גרסתם המקורית.
- **גבול תפעולי:** M3-A/Host Bridge שהיה ב־Draft בעת הסקירה אינו נחשב לגרסה מותקנת; בודקים מציאות עדכנית לפני מימוש.

### TWITO HQ / כלי ניהול פרויקטים

- **ניהול פנימי:** כל פרויקט מנהל בעצמו משימות, החלטות וראיות QA.
- **תיאום רוחבי:** מנגנון אחד מרכז תלות בין פרויקטים, סטטוס וקישורים מאושרים בלבד.
- **מניעת כפילויות:** לא יוצרים משימת־ראי או מסמך־ראי לכל מקור; מעדיפים הפניה ל־Issue/מסמך המקורי.
- **שמרנות בהרשאות:** חשבונות הפקות עצמאיים אינם נכללים אוטומטית בחשבונות התיאום האחרים.

## ד. שערי החלטה לפני הרחבה

**לפני תחילת מיילסטון:** מהו ה־Baseline? מי בעל המידע? איזה חוזה נתונים משתנה? מהו מסלול חזרה לאחור? אילו בדיקות מוכיחות שלא נשברו יכולות?

**בסוף המיילסטון:** האם ניתן לשנות אובייקט או נכס מתוך נתונים בלי לעדכן במקביל קוד קשיח? האם המקורות והגרסאות עקביים? האם התוצרים ניתנים לשחזור? האם תועדו PASS, FAIL ו־NOT TESTED בנפרד?

**אין להרחיב אוטומציה או לייצר עוד שכבות ניהול לפני שהתשובות לשאלות אלה ברורות.**

## ה. תוצרי מינימום מומלצים לכל פרויקט

- `ARCHITECTURE_AUDIT.md` — מצב נוכחי, תלויות, חובות טכניים ומגבלות ראיות.
- `SOURCE_OF_TRUTH_MATRIX.md` — סוג מידע, Owner, מקור מוסמך וצרכנים.
- `SCHEMA_AND_CONTRACTS.md` — מזהים, גרסאות וממשקים עם תאימות לאחור.
- `QA_REPORT.md` — מה הורץ, תוצאות ומגבלות.
- `HANDOFF.md` ו־`CHANGELOG.md` — נקודת המשך והיסטוריית החלטות.
- חבילת שחזור / קוד מקור / תוצר ניתן להרצה — כאשר זה רלוונטי למיילסטון.

## ו. בסיס המקורות ומעמד ההמלצות

העקרונות גובשו מתוך דיוני הארכיטקטורה של **האחים רפאל** ושני דוחות `PROJECT_ARCHITECTURE_ASSESSMENT` של **STAN FAN Studio HQ** מ־27.10.2026. מן הדוחות נלקחו, בין השאר, ההבחנות בין release לסקיל, בין פיילוט ידני לאינטגרציה חיה, בין קאנון ל־Work Orders, ובין נתוני Bible לבין תצוגת HTML. יישום העקרונות במשחק וב־TWITO HQ הוא **המלצה רוחבית**, ולא טענה שהיישום כבר בוצע או עבר QA. פרטי מצב גרסה ו־PR מחייבים אימות מחדש בעת תחילת עבודה.
